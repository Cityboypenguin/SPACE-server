# 利用者がアップロードしたものの扱い

アバター・投稿の添付・DM の添付・規約ドキュメントを、どう受け入れてどう配るか。
形式を増やすとき（PDF など）は、この文書の「形式を増やすとき」だけを見れば足りる。

## 守りたいこと

利用者がアップロードしたファイルの中には、ブラウザーが**実行できるもの**がある。
SVG は図形の指示書で、中にスクリプトを書ける。PDF も同様。

実行された場合に困るのは、**アプリのログイン情報（トークン）を読まれること**。
これができると利用者の成りすましになる。

## 4つの層

安全性は①と③で担保する。②は置き場の選択、④は見た目。

| 層 | すること | 形式を見るか |
|---|---|---|
| ① 受け入れ | 許可リストにある形式か／**中身が名乗りと一致するか** | **見る** |
| ② 保存 | 種別で置き場が決まる（公開／非公開／内部専用） | 見ない |
| ③ 配信 | `Content-Disposition: attachment` を必ず付ける | 見ない |
| ④ 表示 | 形式ごとの見せ方 | **見る** |

**形式による分岐は①と④だけに置く。**②と③に形式の例外を作らないこと。
作ると、形式を増やすたびに安全性を再検討することになる。

## ① 受け入れ — 中身が名乗りと一致することを確かめる

署名付き PUT では **Content-Type も利用者が決める**。保存されたメタデータは
「そう名乗った」という記録にすぎず、中身の保証ではない。中身が HTML の
ファイルを `image/png` と名乗って置ける。

そこで受け入れ時に先頭を読んで、名乗りと一致していることを確かめる
（`internal/upload/sniff.go`）。

- 画像は `http.DetectContentType` で一致を見る。これは MIME Sniffing Standard
  の実装で、**ブラウザーが使うのと同じ手順**。ここで `image/png` と判定された
  ものは、ブラウザーも `image/png` と判定する
- SVG とマークダウンはテキスト形式なのでバイト列で見分けられない。SVG は
  根の要素が `svg` であること、マークダウンは HTML として解釈されない中身で
  あることを見る

**この層は「SVG が持つ危険」を落とさない。**script 入りの SVG は「形式としては
SVG」なので通る。それは③と、下記のホスト分離で受ける。

## ③ 配信 — 文書として開かせない

`Content-Disposition: attachment` を付けると、URL を直接開かれても
ブラウザーは保存ダイアログを出し、**文書として描画しない**。

アプリの表示には影響しない。`<img>` と `fetch()` はこの指定を見ない。
影響するのは「右クリック → 画像を新しいタブで開く」が保存になることだけ。

値は `repository.ServedContentDisposition` に1度だけ書いてある。
置き場の実装はそれを使い、独自の指定を持たない。

付けるのは**受け入れの写し（CopyObject）のとき**。写し先はアプリが参照する
唯一のキーなので、ここで付ければ漏れが無い。

## ホストの分離 — 守る約束

**利用者の保存物を、アプリと同じホストから配らない。**

```
アプリ    ....azurestaticapps.net        ログイン情報はここのオリジンにある
保存物    ....blob.core.windows.net      画像はここから配る
```

ブラウザーはオリジンごとにデータを分けるので、保存物のオリジンでスクリプトが
動いても**アプリのログイン情報には手が届かない**。

これは③と合わせて2段になっている。

- ホスト分離が崩れる例: CDN をアプリと同じホストにパスで相乗りさせる
  （**現行の AWS の CloudFront がそうなっている**）。そのとき③が残る
- ③が崩れる例: 誰かが blob のメタデータを書き換える。そのときホスト分離が残る

**片方だけに全部を背負わせない。**

### CDN を前に置くときの条件

3つが同時にぶら下がる。

1. **別ホストにする**（`img.example.com` など）。アプリのホストに相乗りさせない
2. `Content-Disposition` を素通しする（消すと③が無くなる）
3. ついでに `X-Content-Type-Options: nosniff` を足せる（下記）

## できないこと — nosniff

`X-Content-Type-Options: nosniff` は Azure Blob では設定できない。
Blob が設定させるのは `Content-Type` / `Content-Disposition` / `Cache-Control`
など決まった欄だけで、任意のヘッダーは足せない。

ただしこの穴は①と③でほぼ埋まる。

- ① 中身と名乗りが一致している → 中身が HTML のものが入らない
- ③ attachment が付いている → 文書として開かれない＝推測する機会が無い

埋まらないのは①③の両方が破れたときで、それは nosniff があっても危ない。
前に CDN を置くときに足す。

## 形式を増やすとき

例として PDF を許す場合。

1. **① 許可リストに足す**（`internal/upload` の `Kind.Exts`）。
   そのうえで、中身と名乗りの一致をどう見るかを決める。PDF はマジック
   ナンバー（`%PDF-`）があるので画像と同じ扱いにできる
2. **② 変更なし。** 添付の置き場は種別で決まっている
   （投稿は公開、DM は非公開）
3. **③ 変更なし。** ただし **attachment を外さないこと。**
   外すとブラウザーの PDF ビューアに渡り、スクリプトが動く余地ができる
4. **④ 見せ方を決める。** ダウンロードさせるか、`fetch` で中身を取って
   自前で描画するか（pdf.js など）。`<iframe>` でブラウザーのビューアに
   渡す方法は③と両立しないので採らない

**①と④だけを考えればよい**のが、この構成の目的。

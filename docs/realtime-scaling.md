# 複数インスタンスで動かすための現状整理

## この文書の位置づけ（2026-09-29 全面改訂）

以前のこの文書は「app を2台以上にするなら、これから何を作るか」という**設計メモ**だった。
その後、書かれていた対象はほぼ実装された。いま必要なのは作り方の提案ではなく
**「どこまで済んでいて、何が残っているか」の台帳**なので、そういう文書に書き換えた。

**現状: 本番の app は1台（[compose.ec2.yaml](../compose.ec2.yaml)）。ただし2台にするための
土台はほぼ揃っている。** 残っているのは下の「まだ1台を前提にしているもの」の4件だけで、
いずれも「壊れる」ではなく「緩む・ずれる」に留まる。

## 対応済み

台をまたいでも正しく動くようにしてあるもの。**新しく状態を持つコードを足すときは、
ここに並んでいるものと同じ扱いができるかを先に考えること。**

| 対象 | 実体 | どう解いたか |
| --- | --- | --- |
| GraphQL サブスクリプション | [infra/redis/bus.go](../infra/redis/bus.go) | Redis Pub/Sub へ publish し、各台が subscribe して自分の接続にだけ配る。Go の構造体を流していた箇所は [graph/pubsub_types.go](../graph/pubsub_types.go) のコーデックで JSON に載せ替えた |
| 通知の SSE 配信 | [infra/redis/sse_fanout.go](../infra/redis/sse_fanout.go) | 同上。自分の台のクライアントにも Redis から戻ってきたものを渡す（直接渡す近道を作ると送信元の台にだけ二重に届く） |
| SSE の採番と履歴 | [infra/redis/sse_store.go](../infra/redis/sse_store.go) | イベントIDの採番と履歴を Redis に置いた。台ごとに1から数えると同じIDが別のイベントを指し、`Last-Event-ID` からのリプレイが狂うため |
| 利用規約の配信タイマー | [infra/redis/terms_broadcast.go](../infra/redis/terms_broadcast.go) | 版ごとに `SET NX` で配信権を取り、取れた台だけが配る。起動時に現行版も拾い直すので、発効時刻を停止中に跨いだ版も1回だけ配信される |
| 授業取り込みの排他と進捗 | [infra/redis/course_import_store.go](../infra/redis/course_import_store.go) | 排他は `SET NX` + 心拍で延長、進捗は別キー。管理者が別々の台に当たっても1本しか走らず、進捗もどの台からも見える |
| 活動アーカイブの実行 | [internal/activityarchive/archiver.go](../internal/activityarchive/archiver.go) | 分散ロックを取れた台だけが走る。取れなければ再試行を予約して戻る |
| 速度制限 | [infra/redis/rate_limiter.go](../infra/redis/rate_limiter.go) | トークンバケツを Lua で Redis 上に置いた。読み・計算・書きを Redis 内で1回に閉じてあるので、同時リクエストが互いの書き込みを踏まない |
| DB マイグレーション | [db/migrate.go](../db/migrate.go) | golang-migrate が MySQL のロックを取るので、同時に起動しても1台しか流さない |

## まだ1台を前提にしているもの

**いずれも「壊れる」ではない。** 数え損ねる、緩む、重複して計算する、のいずれか。
台を増やす判断が出たときに、下の4件を「直すか、その状態で許容するか」を決めること。

### 1. 1ユーザーあたりの同時接続数の上限

- 実体: [internal/sse/broker.go](../internal/sse/broker.go) の `maxSSEConnectionsPerUser`（SSE、5）と
  [internal/connlimit/ws.go](../internal/connlimit/ws.go) の `MaxWSConnectionsPerUser`（WebSocket、5）。
  どちらも台のメモリで数えている。
- 起きること: 台ごとに別々に数えるので、実質「5 × 台数」まで張れる。
- 緩和: ロードバランサのセッションアフィニティを有効にすれば、**同じブラウザの接続は
  同じ台に行く**ので「複数タブを考慮して5」という本来の意図は保たれる。緩むのは
  「同じ人が別デバイスから繋いだとき」だけになる。
- 直すなら: Redis の分散カウンタ。ただし素朴に `INCR`/`DECR` すると**台が落ちたときに
  カウントが残り、その利用者が寿命ぶんログインできなくなる**。接続ごとの心拍で
  生存を更新する作りが要る（ここが実装を見送っている理由）。

### 2. 接続数・リクエスト数のメトリクス

- 実体: [internal/metrics/metrics.go](../internal/metrics/metrics.go) の `Global`
  （`atomic.Int64` のカウンタとレスポンスタイムのリングバッファ）。
- 起きること: 管理画面の「WebSocket接続数」などが**自分の台のぶんしか出ない**。
  2台なら実際の半分に見える。表示だけの問題で、動作には影響しない。
- 直すなら: 台ごとの値を寿命付きで Redis に置き、読むときに合算する。
  台が消えたぶんは寿命で自然に落ちるので、心拍は要らない。

### 3. 集計キャッシュ

- 実体: [infra/cache/analytics_cache.go](../infra/cache/analytics_cache.go) の TTL キャッシュ。
- 起きること: 台ごとに別のキャッシュを持つので、期限切れのたびに**同じ集計（サマリーは
  SQL 35本以上）が台数ぶん走る**。singleflight は台の中でしか効かない。
- **結果は正しい。** 遅くなるだけ。
- 直すなら: キャッシュを Redis に移す。キーの作り方は今のままでよい。

### 4. 活動記録の書き込み間引き

- 実体: [internal/middleware/user_activity.go](../internal/middleware/user_activity.go) の
  `UserActivityRecorder`（ユーザーごとの最終記録時刻を台のメモリに持つ）。
- 起きること: 間引きが台ごとになるので、台数ぶん書き込みが増える。
- **DB 側の条件が最後の砦として残っているので、データは壊れない。**
  毎リクエスト撃っていた頃と比べれば桁違いに少ない。同ファイルのコメントに記載済み。
- 直すなら: 間引きの記憶を Redis に移す。ただし書き込み1回を減らすために Redis への
  往復が1回増えるので、割に合うかは要検討。

## 台を増やすときの前提条件

### 最小レプリカ数を 0 にしないこと

SSE と WebSocket は常時接続なので、ゼロスケールすると接続が切れる。
クライアントは再接続するが、その間の通知は届かない。**最小1を維持すること。**

### セッションアフィニティ

配信の正しさのためには**もう必須ではない**（SSE の採番・履歴を Redis に移したので、
再接続が別の台に振られてもリプレイは成立する）。
有効にする意味は上の「1. 同時接続数の上限」を実質的に機能させることにある。

### 規約配信の印について

[infra/redis/terms_broadcast.go](../infra/redis/terms_broadcast.go) の印には**寿命を付けていない**。
付けると寿命切れ後の起動で同じ版をもう一度配ってしまうため。
Redis の `maxmemory-policy` が `allkeys-*` の場合は寿命の無いキーも追い出されうるので、
その構成では同じ版が1回だけ配り直されることがある（クライアントは同意状態を
取り直すだけなので実害は無いが、ログを見て驚かないように）。

## 参考: 以前の設計メモから変わった判断

- **SSE の履歴はローカルのままでよい**（旧文書の記述）→ **Redis に移した。**
  ローカルのままだと、同じ利用者のタブが別々の台に繋がったときに採番が衝突する。
  スティッキーセッション前提で回避する案だったが、履歴を共有するほうが前提が減って素直だった。
- **規約タイマーは DB に配信済みフラグを立てる案 (b) を推奨**（旧文書の記述）→ **Redis の `SET NX` にした。**
  新しいカラムもマイグレーションも要らず、同じ「1回だけ」を得られるため。
  読むのは起動時と発効時だけなので、Redis の可用性に引きずられる場面も少ない。

# リアルタイム配信の水平スケール（将来の複数インスタンス化に向けて）

## 現状（2026-07 時点）

本番は **単一 app インスタンス**（[compose.ec2.yaml](../compose.ec2.yaml)）で運用している。
そのためリアルタイム系はプロセス内メモリ実装で**正しく動作する**：

- [internal/pubsub/pubsub.go](../internal/pubsub/pubsub.go) — GraphQL WebSocket サブスクリプション（DM/未読/既読）。
- [internal/sse/broker.go](../internal/sse/broker.go) — 通知の SSE 配信（履歴リプレイ付き）。

この文書は「app を 2 台以上に増やしたとき」に必要な変更をまとめた**設計メモ**である。
単一インスタンスのうちは実装しない（メリットがなくリアルタイム経路のリスクだけ増えるため）。

## 問題

インスタンス A で発生したイベント（例: ユーザー X が投稿にいいね）を、
別インスタンス B に SSE/WS 接続しているユーザー Y へ届ける手段がない。
接続とイベント発生元が別プロセスに分かれると配信が欠落する。

## 方針: Redis Pub/Sub でファンアウト

Redis は既に導入済み（トークン失効・OTP 等）。これを配信バスとして使う。

1. **発行**: `PublishToUser` / `Broadcast` / `PubSub.Publish` は、ローカル配信の代わりに
   Redis チャンネルへ publish する（ペイロードは JSON）。
2. **購読**: 各インスタンスが起動時に Redis チャンネルを subscribe し、
   受信したイベントを**自分のローカル接続にだけ**配信する（既存の broker/pubsub のローカル配信処理を再利用）。
3. これで発生元に関係なく全インスタンスの接続へ届く。単一インスタンスでも
   「publish → 自分が受信 → ローカル配信」で従来と同じ挙動になる。

### 実装上の注意

- **SSE (broker.go)**: ペイロードが既に `map[string]any` なので JSON 化は容易。
  イベント ID / 履歴はインスタンスローカルのままでよい（SSE 接続はスティッキーにするのが前提。
  ロードバランサで同一ユーザーの SSE を同一インスタンスへ固定する）。リプレイは DB の通知一覧が最終的な真実。
- **PubSub (pubsub.go)**: ここが難所。現在は Go の構造体ポインタ（`*gqlmodel.Message` 等）を
  チャンネルにそのまま流している。Redis を挟むにはトピックごとに **JSON シリアライズ/デシリアライズ**が必要。
  トピック名から具体型を解決するレジストリ（`map[topicPattern]func([]byte) any`）を用意し、
  購読側で正しい型に復元してからローカル配信する。
- **接続数メトリクス** (`metrics.Global.IncSSEConnections` 等) はローカル接続数のまま各インスタンスで計測し、
  全体値が必要なら集計側で合算する。

### 代替案

将来 RDS/ElastiCache などマネージド構成へ移すなら、
GraphQL サブスクリプションを Redis Streams や専用の pub/sub SaaS に載せる選択肢もある。
まずは上記の Redis Pub/Sub ファンアウトが最小変更で確実。

## プロセス内状態の棚卸し（2026-09 追記）

上の章は「リアルタイム配信（PubSub / SSE）」に絞った話だったが、監査の指摘を受けて
**プロセス内メモリにしか存在しない状態**を改めて全部洗い出した。配信経路だけでなく
スケジューラと進捗トラッカーも同じ前提（app は1台）に乗っている。

**現状の前提: 本番の app インスタンスは1台。以下はすべて「1台であること」に依存している。**
インスタンスを増やすときは、下の4つを**まとめて**片付ける必要がある（1つだけ直しても
残りが壊れる）。

### 1. GraphQL サブスクリプションの PubSub

- 実体: [internal/pubsub/pubsub.go](../internal/pubsub/pubsub.go) の `PubSub` 型
  （`subs map[string][]chan interface{}`）。生成は [cmd/server/main.go](../cmd/server/main.go) の `pubsub.New()`。
- 壊れ方: 購読者（WebSocket 接続）と発行者（ミューテーションを処理したインスタンス）が
  別プロセスになると、**イベントが一切届かない**。DM の新着メッセージ、未読数の更新、
  既読の反映が「相手には出るが自分には出ない」「リロードすると出てくる」という形で落ちる。
  ユーザーから見ると壊れているのかラグなのか区別がつかない類の不具合になる。

### 2. 通知の SSE 配信

- 実体: [internal/sse/broker.go](../internal/sse/broker.go) の `Broker` 型
  （`clients map[int64][]*Client` と `history map[int64]*userHistory`）。生成は `sse.NewBroker()`。
- 壊れ方: 通知を発生させたインスタンスと、受信者が SSE を張っているインスタンスが
  別だと**通知トーストが出ない・ベルが更新されない**。
  リプレイ履歴（`history`）もインスタンスローカルなので、再接続が別インスタンスに
  振られると `Last-Event-ID` が噛み合わず、**切断中のイベントがリプレイされない**
  （イベントIDは履歴と同じユーザー単位の連番なので、インスタンスが違えば
  同じIDが別のイベントを指す）
  （通知の本体は DB にあるので消失はしないが、画面が黙る）。
  1ユーザー5接続という上限（`maxSSEConnectionsPerUser`）も**インスタンスごとの数**に
  なるので、実質 5×インスタンス数まで張れてしまい上限として機能しなくなる。

### 3. 利用規約の配信タイマー

- 実体: [usecase/terms/broadcast_scheduler.go](../usecase/terms/broadcast_scheduler.go) の
  `BroadcastScheduler`（`time.AfterFunc` によるプロセス内タイマー）。
  起動時の `SchedulePending` と、作成時の `Schedule` の2経路。
- 壊れ方: **重複発火**する。起動時に全インスタンスが同じ未来バージョンにタイマーを張るので、
  effectiveDate になると台数ぶん `terms_updated` が飛ぶ。逆に作成時のタイマーは
  「作成リクエストを受けた1台」にしか無いため、その台が effectiveDate 前に落ちると
  次の再起動まで配信されない。
- 詳細な制約は同ファイルの型コメントに書いてある。**ここでは繰り返さない**ので、
  直すときはまずそのコメントを読むこと。

### 4. コースインポートの進捗トラッカー

- 実体: [internal/courseimport/tracker.go](../internal/courseimport/tracker.go) の `Tracker`
  （`status Status` を mutex で保護しているだけ）。生成は `courseimport.NewTracker(...)`。
- 壊れ方: 進捗が**インポートを実行した1台でしか見えない**。管理画面のポーリング／
  サブスクリプションが別インスタンスに振られると `IDLE` が返り、走っている最中なのに
  「動いていない」ように見える。さらに「同時に1本だけ」という排他も1台ぶんなので、
  **インスタンスごとに1本ずつ、合計で台数ぶんの取り込みが同時に走りうる**。
  スクレイピング対象サイトへの多重アクセスになるため、これが4つの中では一番実害が大きい。

### 移行するときの選択肢

| 対象 | 選択肢 | 作り直すもの |
| --- | --- | --- |
| PubSub | 外部 Pub/Sub（Redis Pub/Sub が第一候補。Redis は導入済み） | トピックごとの **JSON シリアライズ/デシリアライズ**。現在は Go の構造体ポインタを直接チャンネルへ流しているため、トピック名→具体型のレジストリが要る（上の章の「実装上の注意」参照）。 |
| SSE | 同じ外部 Pub/Sub でファンアウト＋LB のスティッキーセッション | 配信経路の差し替えのみ。履歴はローカルのままでよいが、**同一ユーザーの SSE を同一インスタンスへ固定する**のが前提。固定しないなら履歴も外部化が要る。接続数上限も外部カウンタにしないと効かない。 |
| 規約タイマー | (a) 分散ロック／リーダー選出（Redis の SET NX + TTL）で1台だけがタイマーを持つ / (b) タイマーをやめて全インスタンスが定期ポーリングし、「配信済み」フラグを DB に立てて**取った1台だけ**が配信する | (a) はリーダーが落ちたときの引き継ぎが要る。(b) のほうが状態が DB に残るぶん素直で、再起動にも強い。**(b) 推奨。** |
| インポート進捗 | 状態を Redis（または DB）へ移し、取得も排他もそこで行う | `Tracker` の読み書きを外部ストア越しにする。**排他は「開始時に Redis で SET NX する」形**にすれば、多重起動の防止と進捗共有を同じ仕組みで賄える。`onChange` コールバックは SSE/PubSub の外部化に乗せる。 |

いずれも**単一インスタンスのままなら実装しない**。メリットが無く、リアルタイム経路の
リスクだけが増える。インスタンスを増やす決定が出た時点で、上の4つを1つの作業として扱うこと。

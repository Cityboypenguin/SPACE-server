# 本番切り替え手順（AWS → Azure）

切り替え当日に迷わないための手順書。**順番に意味がある箇所には理由を書いて
ある。**理由を読まずに入れ替えると、データが迷子になるか、戻せなくなる。

前提として、切り替えが終わるまで**本番は AWS**。Azure 側は組み上がっているが
誰も使っていない状態から始める。

---

## 考え方 — 遅い作業と速い作業を分ける

切り替えには性質の違う2つの作業が混ざっている。**混ぜると失敗したときに
戻せない。**

| | 速さ | 戻せるか |
|---|---|---|
| DNS の委任先を移す（お名前.com の設定） | 数時間〜数日 | すぐには戻せない |
| レコードの行き先を変える | 60秒（TTL） | **すぐ戻せる** |

だから**先に委任先だけを移し、行き先は AWS のまま**にしておく。利用者から見て
何も変わらない状態で、遅い作業を終わらせる。当日やるのは速くて戻せる作業だけ。

---

## 第1段階：DNS の引っ越し（利用者に影響なし）

**この段階が終わっても、利用者からは何も変わらない。**行き先は CloudFront の
ままで、AWS が応答し続ける。

### 1-1. ゾーンに今と同じ内容を入れる

Azure DNS ゾーン `senshu-universe.com` に、Route 53 と**同じ行き先**を入れる。

| 名前 | 種別 | 行き先 |
|---|---|---|
| `@` | A（別名ではなく CNAME 相当が使えないので下記注意） | CloudFront |
| `www` | CNAME | `d2ihoct532mxwc.cloudfront.net` |
| `_1ef994eb5fec5fad12064663a823b487` | CNAME | ACM の検証値 |
| `_32fbeb6eccc34af5e9430f9e2e410576.www` | CNAME | ACM の検証値 |

`@`（www の付かない形）には CNAME を書けない。Route 53 では ALIAS で
CloudFront を指していた。Azure DNS の別名レコードは **Azure 資源しか**
指せないので、CloudFront は指せない。

**したがって `@` は次のどちらかにする。**

* CloudFront の IP を A レコードで直接書く（**非推奨**。CloudFront の IP は
  予告なく変わる。引っ越し期間だけの暫定として、変わっていないか毎日見る）
* 引っ越しと切り替えを同じ日にやる（`@` は最初から Azure を指す）

**後者を推奨する。**`@` だけは暫定状態を作らない。つまり第1段階で移すのは
`www` と検証用2件、`@` は第3段階で初めて書く。

> ACM の検証用2件を持っていく理由は、AWS の証明書を更新できる状態を保つため。
> 消すと証明書が切れたあとは AWS に戻れない。戻り道を残す分の費用はゼロ。

### 1-2. 切り替える前に、名指しで確認する

**ここを飛ばさない。**世界はまだ Route 53 を見ているので、Azure 側だけを
名指しで問い合わせれば、本番に影響なく答え合わせができる。

```bash
# ゾーン作成時に割り当てられたネームサーバーを確認
az network dns zone show -g Senshu-network-education2-RG \
  -n senshu-universe.com --query nameServers -o tsv

# そのサーバーに直接聞く（世界への影響はゼロ）
dig @ns1-NN.azure-dns.com www.senshu-universe.com
dig @ns1-NN.azure-dns.com _1ef994eb5fec5fad12064663a823b487.senshu-universe.com CNAME
```

**Route 53 と同じ答えが返ることを確かめてから次へ進む。**

### 1-3. お名前.com のネームサーバーを書き換える

お名前.com → ドメイン → ネームサーバーの設定 → 「その他のネームサーバーを
使う」に、1-2 で確認した4つを入れる。

浸透を待つ（数時間〜数日）。待っている間も**行き先は AWS のまま**なので、
利用者には影響しない。

```bash
# 世界から見たネームサーバーが入れ替わったか
dig +short NS senshu-universe.com    # azure-dns 系になれば完了
```

## 第2段階：Azure 側を本番と同じ状態にする（まだ切り替えない）

### 2-1. VM を HTTPS にする

先生に DNS 名ラベルをいただいた後。

443 番は **NSG で既に許可されている**（確認済み）。判別の方法を残しておく。
外から 443 を叩くと「即座に接続拒否」が返り、遮断されている番号（9999 など）は
「無応答で時間切れ」になる。拒否が返るのはパケットが VM まで届いた証拠なので、
VM に何も置かずに許可の有無が分かる。

```bash
curl -v --connect-timeout 10 http://20.243.81.35:443/   # 即座に拒否 → 許可あり
curl -v --connect-timeout 10 http://20.243.81.35:9999/  # 時間切れ   → 遮断
```

```bash
sudo certbot --nginx -d senshu-space.japaneast.cloudapp.azure.com
# deploy/azure/nginx.conf に listen 443 と証明書のパスを入れ、80 は
# リダイレクトにする。更新は snap.certbot.renew.timer が動いている
```

### 2-2. クライアントを main に入れる

**SWA は `main` から建てる。**アップロード修正（`03a7642`）は `Azure`
ブランチにしか無いので、入れないとアップロードが全部失敗する。

```bash
# SPACE-client
git checkout main && git merge Azure && git push origin main
```

**この時点で本番は変わらない。**`@` はまだ CloudFront を指しているので、
`main` を更新しても影響を受けるのは SWA の既定ホスト名だけ。

### 2-3. API の場所を設定する

GitHub のリポジトリ変数 `VITE_API_URL` を Azure の API に向ける。
（SWA のビルドで埋め込まれるので、変えたら再ビルドが必要）

### 2-4. 既定ホスト名で通して確認する

```
https://victorious-island-00bb94300.5.azurestaticapps.net
```

**本番のドメインを使わずに、Azure だけで一通り動くことを確認する。**
特にアップロード（アバター・添付・規約）は必ず試す。

## 第3段階：切り替え当日

**ここから先は利用者に影響する。**所要は DB の大きさ次第だが、現状
1.7MB なので数分で終わる見込み。

### 3-1. メンテナンスを有効にする

管理画面から（内部は GraphQL の `toggleMaintenanceMode(enabled: true)`）。
**AWS 側で有効にする。**管理者以外の要求が 503 になる。

> 注意：この旗は Redis に保存されるが、各プロセスは**自分のメモリ**にも
> 持っている。アプリが複数動いている環境では、切り替えた1台にしか効かない。
> 現状 AWS は1台なので問題にならないが、増えていたら全台を確認する。

### 3-2. 最後のバックアップを取る

```bash
# AWS 側で最新の DB を書き出す（戻り道の確保）
```

### 3-3. DB を移す

AWS の DB を書き出して Azure の MySQL へ入れる。

```bash
# 入れたあとに件数を確認する。utf8mb4 を必ず指定する
#（指定しないと日本語が壊れる。別途メモあり）
mysql --default-character-set=utf8mb4 ...
```

### 3-4. 画像の差分を移す

前回の一括移行（993件）以降に AWS 側へ増えたものを運ぶ。
`azcopy` は使えないので、取得してから PUT する。

### 3-5. DM の添付を移す

```bash
scripts/migrate_message_media.sh
```

**必ず 3-3 と 3-4 の後に実行する。**このスクリプトは DB のレコードを見て
対象を決め、移動後に DB のキーを書き換える。順番を逆にすると、

* 3-3 より前に実行 → 書き換えた DB が、後から入れた古い DB で上書きされる
* 3-4 より前に実行 → まだ Blob に無いものを探して失敗する

### 3-6. DNS の行き先を Azure に向ける

Azure DNS のレコードを書き換える。**ここが実際の切り替え。**

| 名前 | 種別 | 行き先 |
|---|---|---|
| `@` | 別名（ALIAS） | Static Web Apps |
| `www` | CNAME | Static Web Apps の既定ホスト名 |
| `api` | CNAME | `senshu-space.japaneast.cloudapp.azure.com` |

**TTL は 60 秒にしておく。**戻すときの速さがこれで決まる。

SWA 側にもカスタムドメインを登録する（`senshu-universe.com` と `www`）。
検証用の TXT レコードを求められるので、ゾーンに追加する。

### 3-7. 許可する接続元を揃える

```
ALLOWED_ORIGINS（/opt/space/.env）に https://senshu-universe.com が
入っていること（現在入っている）
Blob の CORS 許可元に同じものが入っていること（現在入っている）
```

### 3-8. メンテナンスを解除して確認する

**最低限ここを見る。**

```
ログイン / 投稿の表示 / 画像の表示
アバターのアップロード  ← 2-2 を忘れていると、ここで失敗する
DM の送信と添付の表示
通知（SSE）が届くか     ← nginx の設定が効いているかの確認
```

---

## 戻し方

**第3段階で問題が出たら、Azure DNS のレコードを CloudFront に戻す。**
TTL 60秒なので1分程度で戻る。AWS 側は止めていないのでそのまま動く。

**だから第4段階までは AWS を止めない。**

---

## 第4段階：AWS を片付ける（数日様子を見てから）

```
1. 数日間、Azure で問題が出ないことを確認する
2. AWS の EC2 / S3 / CloudFront を停止する
3. ALLOWED_ORIGINS から CloudFront の URL を外す
4. Azure DNS から ACM の検証用レコード2件を削除する
5. Route 53 のホストゾーンを削除する（月 0.50 USD の停止）
```

**4 と 5 は最後にする。**これを消すと AWS へ戻れなくなる。
